# v17：搬入・定着を評価する物理beamサーチ（検証用）

配置だけを探索して後から搬入順序を選ぶ方式に代えて、1つの枝を「その順序で搬入・定着させた後の全荷物の物理状態」として扱う。C++で幾何学的な候補を絞り、PyBullet DIRECTで搬入と定着を実行し、両方に成功した候補だけを子の枝として残す。

## 枝の展開

1. 各枝の実位置・実姿勢からEP候補を作る。
2. 次に積む荷物も分岐させ、向き・配置位置の候補を生成する。
3. 親の予測状態から独立した物理シーンを再構築する。
4. float32で実際に発行する座標を使い、元のPlacementValidatorで包含・Y→X搬入・定着を確認する。
5. 成功時は新しい荷物だけでなく全荷物の位置・姿勢・速度を子へ保存する。追加荷重で支持荷物が沈んだ場合も、その状態が次の判定に使われる。
6. 元のEvaluatorによる定着後の体積充填率を優先し、積載数・公称体積・重心などを副指標としてbeamを絞る。

普通のEPが幾何学的に有効でも搬入できないことがあるため、投影EPも同じ候補集合に含める。右側床EPも追加した。初手の荷物が同じ枝への集中を抑える。

本版はbeamによる近似探索であり、大域的な最適配置の保証はない。未採用の荷物はAPIが要求する全荷物順列の末尾へ追加する。APIには荷物のスキップがないため、その荷物に実行可能候補がなければ停止する。

## 物理モデル

src/ground_handlingのContainer・Item・PlacementValidator・Evaluatorをそのまま再利用する。公式実装やC++コードを変更しない。独立したDIRECT接続なので本番環境の状態を探索中に動かさない。

柔らかい荷物は固定GEOM_BOXにcontactStiffness/contactDamping等を適用する元のモデル。形状圧縮や独自の物理法則を追加するものではない。

各枝は位置・姿勢・速度から再構築する。接触ソルバーのwarm-startキャッシュ、内部接触履歴、実環境の未観測速度は複製できない。予測と実環境の完全一致を保証しない。観測から作る初期速度はゼロとし、探索内では速度を引き継ぐ。

実行時には最新観測から発行予定の候補を物理確認する。拒否された場合は、見えている荷物だけで短い物理beamを行う。オフラインで得た全荷物の順序を、実行中に勝手に変更する機能はない。

## 設定と時間制限

| 変数 | 既定値 | 意味 |
|---|---:|---|
| SC_PHYSICS_BEAM | 8 | 保持する物理状態数 |
| SC_PHYSICS_BRANCH | 2 | 荷物・親の組ごとに保持する成功配置数 |
| SC_PHYSICS_ITEM_BRANCH | 8 | 次の搬入荷物を探す窓幅 |
| SC_PHYSICS_CANDIDATES | 16 | 幾何学的上位候補の物理確認数上限 |
| SC_PHYSICS_TRIALS | 3 | 構築順序の試行数上限 |
| SC_PHYSICS_SECONDS | 60 | optimizeの探索予算（最大150秒） |
| SC_PHYSICS_POLICY_SECONDS | 2 | policy再探索の予算（最大5秒） |

予算は候補の間で確認するため、最後の1候補の生成・物理計算分だけ超過し得る。厳密な打ち切りには本番のrunnerのタイムアウトが適用される。

観測にvalidator設定が含まれないため、ローカル実行の--config-pathから観測に一致する設定を取得する。引数がない場合はSC_PHYSICS_CONFIGを指定する。曖昧な設定や設定不明の場合はエラーにし、勝手な物理設定で予測しない。提出先で設定取得ができることは未検証であり、今回はローカル検証用とする。

## 検証

scripts/test_physics_beam.pyの6テスト：元validatorとの1荷物の結果一致、親と兄弟枝の分離、定着失敗の枝除外、枝ごとの姿勢変換、搬入順序の変更、追加荷重による支持荷物の姿勢更新。PyBullet DIRECTで通過した。

実評価は開発用101・103・112・123と元000・001。保留用ケースは使用していない。実行結果と過程はdocs/v17_physics_beam_validation.jsonに保存する。比較元v15はPR #3の保存済み基準であり、同時負荷の対照実験ではない。

方式を確認する初回試作と候補・順序の分岐を増やした試作も記録する。実際に計測したagent.pyのハッシュが保存されていない旧試作は、最終版の評価と混同しない。

## ローカル実行

Python 3.12の環境で、リポジトリのルートから実行する。

```bash
python -m scripts.run_test_visual \
  --config-path cases/101.json \
  --module-path agents/v17_submit/ \
  --result-dir results/v17_actual_101/ \
  --result-fname evaluation.json \
  --verbose True --render-mode human
```

このmodule-pathは配布ZIPをagentsへ展開した場合。GitHub版ではagents/search_cand_v17_physics_beam/を指定する。GitHub版はv16/v15/v14のコードと既存checkerに依存する。ZIPは依存コード、元モデルのコピー、v15と同じPython 3.12用.soを同梱する。

配置図と予測診断を保存する場合、実行前に次を設定する。

```bash
export EP_NEED_3D_BPP="$PWD/results/v17_actual_101/bpp_layout.json"
```

physics_prediction.jsonには候補の物理拒否理由と集計を保存する。run.logのV17-BEAM・V17-ORDER・V17-RUNTIME-REJECT・V17-RUNTIME-REPLAN・V17-ISSUEDで探索と実行を区別する。定着後の内部状態は探索用であり、bpp_layout.jsonの最終目標位置と同一ではない。

## 採用判断

物理状態を持つbeamを実装したことと、v15より高いスコアが得られることは別。現段階でスコアの改善は確認できておらず、v15提出版を置換しない。次は探索の候補分布・beam幅・先読み評価を調べる。物理判定を緩めて見かけの改善を作らない。

## 最終版の実評価結果

| ケース | v15基準の実積載 | v17実積載 | v17体積充填率 |
|---|---:|---:|---:|
| 101 | 22/41 | 10/41 | 16.6098 |
| 103 | 26/41 | 10/41 | 16.6098 |
| 112 | 15/32 | 6/32 | 6.3911 |
| 123 | 15/41 | 6/41 | 9.6784 |
| 000 | 30/41 | 10/41 | 16.6098 |
| 001 | 17/42 | 6/42 | 6.2213 |

6課題で評価エラーなし。オフライン最適化は約60秒、policyの最大値は約2.05秒で、検証した180秒/8秒制限内だった。停止は実行可能な物理候補がないことによるSAFE-ABORT。物理beamの機構は実装・検証できたが、候補分布と探索幅に制約があり、v15より積載数が少ないため未採用。全30ケースの改善を主張しない。
